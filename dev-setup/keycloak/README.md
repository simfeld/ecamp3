# Keycloak third-party API access (local-dev proof of concept)

This is a throwaway, **local-dev-only** proof of concept for letting a third-party
application obtain a token to call the eCamp API on a user's behalf, via Keycloak as a
separate OAuth authorization server. It does **not** touch the existing eCamp login
(username+password, Google, Hitobito), which keeps using Lexik JWT as before.

See `App\Security\OAuth\KeycloakBearerAuthenticator` for how the API accepts these tokens.

## Prerequisites

```bash
docker compose up -d
```

The `ecamp` realm, the test user, the `third-party-demo-app` client, and the demo app's
static file server are all set up automatically on container start
(`dev-setup/keycloak/realm-export.json` and the `keycloak-demo-app` service).

## UI-based walkthrough (recommended)

Open **http://localhost:3000/demo/** — a minimal, dependency-free vanilla-JS page
(`dev-setup/keycloak/demo-app/index.html`) that plays the role of a third-party
application:

1. Click "Sign in with eCamp Connect (via Keycloak)". The page generates its own PKCE
   `code_verifier`/`code_challenge` client-side and redirects to Keycloak.
2. On Keycloak's login page, either log in with `test@example.com` / `test` (Bi-Pi), or
   use one of the "Or sign in with" Hitobito links (see below) with a different persona.
3. You're redirected back to the demo app, which exchanges the code for a token directly
   from the browser (no backend involved — `third-party-demo-app` is a public client, and
   Keycloak allows CORS from `http://localhost:3000` per its `webOrigins` config) and shows
   the decoded token claims.
4. Enter an eCamp user id (e.g. `9145944210a7` for Bi-Pi, `dac7116e02ed` for Luke
   Skywalker) and click "GET /api/users/{id}" to call the real eCamp API with the token and
   see the raw JSON response.

**Switching identities between tests?** Keycloak keeps its own SSO session in a regular
browser cookie (not `sessionStorage`), shared across every tab in that browser profile —
opening a fresh tab does **not** give you a clean Keycloak session. If you sign in as one
user and later click "Sign in" again expecting a different one, Keycloak may silently reuse
the existing session and hand back the same user's token without showing a login page at
all. Always check the decoded `email` claim shown on the demo page before trusting which
user you're testing as; to force a real re-login, either open Keycloak's account console
(via the admin console, or `/keycloak/realms/ecamp/account/`) and log out there, or just use
a private/incognito window per identity you want to test.

## Manual authorization-code + PKCE walkthrough (curl only, no UI)

Useful for scripting or debugging without a browser. The redirect URI is still
`http://localhost:3000/demo/` (the demo app is the only registered redirect target), but
this flow never actually loads that page — it stays entirely in curl, reading the `code`
straight out of the `Location` response header instead of letting a browser follow the
redirect. That matters: if you _do_ open the authorize URL in a real browser and log in,
the demo app's own JS will immediately try to exchange the code itself using whatever PKCE
verifier is in its `sessionStorage` — which won't match one you generated by hand here, so
that exchange will fail (and the code gets burned in the process, since codes are one-time
use). Keep this walkthrough curl-only, or use the UI walkthrough above instead of mixing
the two.

```bash
CODE_VERIFIER=$(openssl rand -base64 96 | tr -d '=+/\n' | cut -c1-64)
CODE_CHALLENGE=$(printf '%s' "$CODE_VERIFIER" | openssl dgst -sha256 -binary | openssl base64 | tr -d '=' | tr '+/' '-_' | tr -d '\n')
AUTH_URL="http://localhost:3000/keycloak/realms/ecamp/protocol/openid-connect/auth?client_id=third-party-demo-app&response_type=code&scope=openid%20ecamp-api&redirect_uri=http://localhost:3000/demo/&code_challenge=$CODE_CHALLENGE&code_challenge_method=S256"

# log in and capture the redirect's Location header without ever loading the page body
rm -f /tmp/kc_cookies.txt
FORM_ACTION=$(curl -s -c /tmp/kc_cookies.txt "$AUTH_URL" | grep -o 'action="[^"]*"' | head -1 | sed 's/action="//;s/"$//' | sed 's/\&amp;/\&/g')
LOCATION=$(curl -s -b /tmp/kc_cookies.txt -D - -o /dev/null \
  --data-urlencode "username=test@example.com" --data-urlencode "password=test" --data-urlencode "credentialId=" \
  "$FORM_ACTION" | grep -i "^location:")
CODE=$(echo "$LOCATION" | grep -o 'code=[^&]*' | cut -d= -f2)

curl -s http://localhost:3000/keycloak/realms/ecamp/protocol/openid-connect/token \
  -d grant_type=authorization_code -d client_id=third-party-demo-app -d code="$CODE" \
  -d redirect_uri=http://localhost:3000/demo/ -d code_verifier="$CODE_VERIFIER" | tee /tmp/keycloak-token.json
ACCESS_TOKEN=$(jq -r .access_token /tmp/keycloak-token.json)
curl -s http://localhost:3000/api/users/9145944210a7 -H "Authorization: Bearer $ACCESS_TOKEN"
```

## Hitobito (pbsmidata / cevidb / jubladb) identity brokering

Unlike the password test user above, Google/Hitobito-authenticated eCamp users don't need
a duplicated password in Keycloak at all: Keycloak brokers directly to the same mock
Hitobito instances eCamp's own login already uses (`App\OAuth\MockHitobito`), via a
Keycloak **identity provider** per instance (`pbsmidata`, `cevidb`, `jubladb` in
`realm-export.json`). To sign in through one instead of the local password form, add
`&kc_idp_hint=pbsmidata` to the authorize URL — this skips straight to the mock provider's
own login page, where you can pick any persona (or type a custom email in the last form).

Avoid the `test@example.com` persona button here (see the account-collision note below);
use the custom form with a different seeded dev user instead, e.g.:

```json
{
  "sub": "luke@skywalker.com",
  "email": "luke@skywalker.com",
  "given_name": "Luke",
  "family_name": "Skywalker",
  "first_name": "Luke",
  "last_name": "Skywalker",
  "nickname": "luke",
  "id": 2001
}
```

**Include `sub` explicitly**, as above. The custom form's hidden `username` field (which
`mock-oauth2-server` otherwise falls back to for the token's `sub` claim) has no value in a
real browser — its `placeholder` is cosmetic on a `type="hidden"` input, so it always submits
empty. Without `sub` in the claims JSON, the resulting token has no usable subject, and
Keycloak's broker throws a `NullPointerException` (`BrokeredIdentityContext.getId()` is
null), surfacing to the browser as a 502.

Note on the `issuer` value in each identity provider's config: `mock-oauth2-server` derives
its self-reported `iss` claim from the request's `Host` header, so it differs depending on
how it's reached (e.g. `http://localhost:3000/pbsmidata` via the browser-facing Traefik
route vs `http://mock-oauth2:8080/pbsmidata` container-to-container). Since Keycloak calls
`tokenUrl`/`userInfoUrl`/`jwksUrl` itself (server-to-server, never through the browser),
those are pointed directly at `http://mock-oauth2:8080/...` and `issuer` is set to match
that same value — only `authorizationUrl` (browser-facing) goes through Traefik. A real
Hitobito instance wouldn't have this quirk, since its issuer is a fixed public URL.

One real, non-obvious behavior surfaced by this: if the same email is used both for the
local Keycloak password user (`test@example.com`) **and** a broker login (e.g. logging in
as `test@example.com` via the pbsmidata mock persona), Keycloak does **not** silently merge
them — it shows an "Account already exists" confirmation page requiring the user to link
the two explicitly. This is different from eCamp's own `HitobitoAuthenticator`, which
auto-links by email with no confirmation step at all. Worth keeping in mind for a real
third-party-access design: it's a legitimate collision safeguard, but a UX difference from
eCamp's current login behavior. Using a different email per test avoids it (e.g.
`luke@skywalker.com`, another seeded dev user, has no local password user to collide with).

## Optional: real MiData integration (pbs.puzzle.ch), not mocked

Everything above brokers to `mock-oauth2-server`. To instead test against the **real**
MiData/Hitobito instance the dev deployment actually uses
(`https://pbs.puzzle.ch`, confirmed reachable and its OIDC discovery/endpoint shapes
verified), run:

```bash
docker compose up -d keycloak
./dev-setup/keycloak/setup-real-pbsmidata.sh
```

This registers an additional `pbsmidata-real` identity provider via Keycloak's Admin REST
API, reusing the exact same `OAUTH_PBSMIDATA_CLIENT_ID`/`OAUTH_PBSMIDATA_CLIENT_SECRET`
eCamp's own login already uses in local dev (`api/.env.dev.local`, gitignored). The script
reads the secret straight out of that file and never writes it anywhere in this repo —
**`realm-export.json` deliberately does not carry this identity provider**, since Keycloak's
realm-import JSON does not support `${env.VAR}`-style substitution (confirmed empirically:
it stores such placeholders as a literal string, not a resolved value), so there was no way
to keep the real secret out of a committed file otherwise.

Because Keycloak's dev-mode storage is ephemeral, **re-run the script every time the
`keycloak` container is recreated** (e.g. after `docker compose rm -sf keycloak`).

To use it, add `&kc_idp_hint=pbsmidata-real` to the authorize URL (or add its "PBS MiData
(real, pbs.puzzle.ch)" link to the demo app the same way the mocked ones already appear on
Keycloak's login page). I verified the OAuth app's redirect-URI handling accepts Keycloak's
broker callback (`.../broker/pbsmidata-real/endpoint`) — a real, empirical request against
`https://pbs.puzzle.ch/oauth/authorize` redirects to the actual sign-in page rather than an
error — but completing the flow needs a **real MiData account**, which only you have.

## Password federation: a real User Storage SPI (Java)

Everything above is config-only. This one piece is genuinely different: a compiled Java
Keycloak extension (`dev-setup/keycloak/spi/ecamp-user-storage/`) that validates password
logins **live** against eCamp's own `POST /authentication_token` endpoint, instead of
storing or verifying a password hash inside Keycloak. This exists because Keycloak has
never shipped built-in bcrypt support (verified via
[keycloak/keycloak discussion #47037](https://github.com/keycloak/keycloak/discussions/47037)
and Keycloak's own `serverinfo`, which only lists `argon2`/`pbkdf2*` as built-in
`password-hashing` providers) — see the "password migration" discussion in this
conversation for the full comparison against a hash-migration approach instead.

### Building and deploying

```bash
docker compose run --rm keycloak-spi-builder   # compiles target/ecamp-user-storage-spi.jar
docker compose up -d keycloak                  # picks it up: mounted at /opt/keycloak/providers/
```

Unlike the theme/CSS changes elsewhere in this POC, **this has no hot reload** — every
Java code change needs a rebuild (`keycloak-spi-builder`) and a Keycloak container
recreate to pick up the new JAR (`start-dev` mode auto-augments on every startup, so no
manual `kc.sh build` step is needed — that's specific to production mode).

### What it actually does

`EcampUserStorageProvider` implements Keycloak's `UserStorageProvider` +
`UserLookupProvider` + `CredentialInputValidator` interfaces (found by inspecting the
actual JARs in the running container — they live in the `keycloak-model-storage` Maven
artifact, not `keycloak-server-spi` as some version-specific docs suggest). Its `isValid()`
POSTs the submitted username/password straight to `http://api:3001/authentication_token`
(the same endpoint used throughout this whole POC) and treats a `204` as success. The
password is never persisted anywhere in Keycloak.

Verified end-to-end against `luke@skywalker.com` (a real eCamp dev-fixture password user,
not the hardcoded local Keycloak `test@example.com` user, to make sure the SPI itself —
not a coincidental match — was doing the work): logged in through Keycloak's normal
password form, obtained a token, and called the eCamp API with it — `200`,
`"displayName": "Luke Skywalker"`. Also confirmed a wrong password is correctly rejected
(fails closed).

### Known limitations of this implementation specifically

- **`getUserByUsername` doesn't do a real existence check.** Any syntactically-plausible
  email is treated as a potentially-real user; the actual gate is the live password check.
  eCamp doesn't currently expose a public "does this email exist" endpoint
  (`GetCollection` on `/users` is `security: 'false'`) — a non-POC version should add one
  and call it here.
- **First login for each federated user hits Keycloak's "Verify Profile" step**, since
  `EcampUserAdapter` doesn't populate `firstName`/`lastName` at all (only email). Whatever
  gets typed there is stored in Keycloak's own federated-storage tables, decoupled from
  eCamp's real profile data — it won't stay in sync if the user later changes their name
  in eCamp. A real implementation should have the adapter fetch and set these from eCamp.
- **Fails closed on error**: a network error or timeout calling eCamp's API rejects the
  login attempt rather than treating an unreachable backend as a valid password.
- Two real bugs surfaced and fixed while building this (documented in git history/code
  comments): the Maven dependency for `UserStorageProvider` was initially wrong
  (`keycloak-server-spi` doesn't contain it), and the realm-import JSON's component
  representation doesn't accept a `providerType` field on each component (it's implied by
  the outer map key) — both were caught by actually compiling and importing, not assumed.

## Known limitations (intentional, out of scope for this POC)

- No self-service client registration — `third-party-demo-app` is the only registered
  client, defined statically in `realm-export.json`.
- No live sync between Keycloak users and eCamp accounts — the token's `email` claim must
  match an existing eCamp `Profile`, matched at request time, not provisioned automatically.
- No scope-to-permission mapping — any request bearing a validly-signed token for the
  `ecamp-api` audience gets the full `ROLE_USER` access of the matched eCamp account.
- The password-login collision behavior described above isn't handled specially; it's
  Keycloak's default, unmodified.
